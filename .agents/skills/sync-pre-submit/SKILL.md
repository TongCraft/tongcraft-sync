# Sync 提交前检查

让交付结果能被维护者复现和继续处理：选对本地检查、处理失败、指出未验证项，并给出对应报告和产物。此流程不额外授予提交、推送、部署或发布权限，执行用户已经授权的操作即可。

检查选择以 [AGENTS.md](../../../AGENTS.md) 的任务路由为入口，命令与覆盖范围以 [本地检查指南](../../../docs/LOCAL_CHECKS.md) 为准。命令从仓库根目录执行。

## 选择必要的证据

查看当前分支、已提交的任务差异、暂存/未暂存修改和相关未跟踪文件。使用用户或实际 PR 的基准；没有分支基准时明确当前检查覆盖的范围，不把工作区差异当作所有分支差异。

确认本次改动已按 [sync-change-review](../sync-change-review/SKILL.md) 审查。已有审查有效时直接使用其结论，不重复同一轮审查。

根据受影响的行为选择 AGENTS.md 路由中的检查；涉及多个模块时取必要检查的并集。只有改动广泛、无法可靠缩小范围、用户要求或排查完整检查失败时才选择 all。Node 服务独立改动可用 `check-services.mjs --target node`，无需为此安装 Cloudflare 工具。

纯文档、Skill 或 AGENTS.md 修改检查 frontmatter、引用路径、命令和路由是否正确；有可用的 Skill 校验器时运行它。若没有修改运行代码、版本或检查实现，无需为了文案变动启动 Minecraft。检查脚本或相关配置变化按路由执行 quick，再执行受影响的 profile。

可复用已有报告中的相关结果，前提是其受影响源码、依赖、配置、运行环境与测试选择仍然适用。代码变化使某项证据失效时重跑那一项；不要仅因提交或推送动作重复已通过检查，也不要把旧报告写成当前所有改动都通过了全量检查。

## 执行和处理失败

- doctor 报告环境缺失时，修复任务范围内的开发环境或记录具体阻塞；不要为了本地测试要求贡献者登录 CF。工具版本、配置和图形环境要求以本地检查指南为准。
- 从终端输出定位本次 `.checks/.../report.json`，核对 profile、执行命令、代码与工作区状态、退出结果、日志和实际执行的测试。检查期间源码变化的报告不能作为最终通过证据。
- 构建失败时，禁止用旧 JAR 补充“构建成功”的结论。产物路径与版本以 client/port 检查结果为准，不选择目录中时间最新的文件代替它。
- 区分断网、依赖缺失、图形环境阻塞与实际回归。保留具体错误和失败场景，完成可独立推进的工作；不能通过跳过测试、移除断言或降低资源限制来制造通过。
- 游戏或界面改动查看本次截图；需要证明旋转、镜像或多子区域行为时运行对应新增场景。当前游戏测试和模拟认证的覆盖范围有明确限制，不等同于完整几何验证或双正版客户端联调。
- 出现用户中断时停止当前流程并报告现状；检查失败可以修复后重跑受影响部分。只有确实完成的检查才能记为通过。

## 交付

简要说明行为变化、实际执行的检查及结果、报告路径、适用的 JAR 版本与路径，以及具体未验证或阻塞事项。没有 JAR 产物的任务无需添加产物项。界面变化附本次截图；提交或 PR 的说明还应包含必要的复现和预期结果。

必要检查失败或阻塞时仍可按用户要求交付部分工作、失败报告或草稿，但明确标记尚未准备好合并/发布。用户已授权提交或推送时按既有授权完成，并如实保留验证状态；本地通过不代表未运行的远端检查或线上联调通过。
